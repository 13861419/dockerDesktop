# 第 7 层：监控与回滚手册

> 七层变更防御的最后一环：发布可追溯、运行可观测、出事能回滚、事故变资产。
> 最后更新：2026-10-28

---

## 1. 发布流程（已自动化）

推送 `v*` 格式 tag 即触发 `.github/workflows/release.yml`：

```
push tag v1.94.0
      │
      ▼
┌─────────────────┐
│ gate 发布门禁    │  server 单测 + web/server 类型检查，不过不发
└───────┬─────────┘
        ▼
┌─────────────────────────────────────────────┐
│ 四平台构建：Windows zip / deb / rpm / macOS  │
└───────┬─────────────────────────────────────┘
        ▼
┌─────────────────┐
│ checksums       │  sha256sums.txt 附到 Release
└───────┬─────────┘
        ▼
┌────────────────────────────────────────────┐
│ 分发：Homebrew tap / ghcr.io 多架构镜像 /   │
│ npm 包 / GitHub Pages APT-YUM 仓库          │
└────────────────────────────────────────────┘
```

**规则：发版只走 tag，tag 只打在 main（且 main 受第 1~6 层保护），测试不过一律不发。**

## 2. 监控能力盘点

| 能力 | 位置 | 说明 |
|---|---|---|
| 健康检查（含版本） | `GET /api/health` | 返回 `status / time / version`，监控侧据此确认线上跑的是哪个发布版本 |
| Prometheus 指标 | `GET /metrics` | 内置可选 token 鉴权（`routes/metrics.ts`） |
| 应用内告警 | `server/src/alerting.ts` | 告警规则引擎 |
| 健康检查探针 | `/api/health-check`（需登录） | 对被管 Docker 站点的探活 |

**最低监控基线建议**：对 `/api/health` 做周期探活 + 版本比对——版本号与预期发布版本不一致 = 部署漂移，立即告警。

## 3. 回滚预案（分渠道）

| 渠道 | 回滚方式 |
|---|---|
| GitHub Release（zip/deb/rpm） | 重新下载**上一个 tag** 的产物安装覆盖；所有历史版本永久保留 |
| ghcr.io Docker 镜像 | 将 `:latest` 指回旧版本：`docker buildx` 重建旧 tag 镜像，或部署时直接引用 `ghcr.io/13861419/dockerdesktop:v1.92.0`（历史 semver tag 镜像永久保留） |
| npm 包 | 已发布版本不可撤回，发 patch 版本（如 v1.93.1）覆盖 latest |
| APT/YUM 仓库（Pages） | Pages 每次发版全量覆盖；回滚 = 对旧 tag 重跑 release 工作流刷新仓库元数据 |
| Homebrew tap | formula 指向最新版，回滚 = 手动改回旧版 sha256（或重发旧版） |

**数据库（SQLite）回滚红线**：schema 变更必须幂等兼容存量库（REVIEW.md 高风险区第 5 条），因此**回滚旧版本代码不需要回滚数据库**——这是回滚能快的前提，破坏此约定 = 锁死回滚路。

## 4. 事故即评测集

**约定：任何逃逸到线上/用户侧的事故，复盘后必须沉淀以下至少一项，否则复盘不算完成：**

1. 一条回归测试（优先加入 `npm run regression:*` 脚本套件或单测）；
2. 一条 REVIEW.md 高风险区规则（让 AI 审查与人审都盯着同类问题）；
3. 一条工作流/流程改进（属于哪一层的防线失守，就补哪一层）。

### 事故复盘模板（复制使用）

```markdown
# 事故复盘：<标题>

- **日期 / 版本**：YYYY-MM-DD / vX.Y.Z
- **现象**：用户侧/监控侧看到什么
- **影响面**：影响谁、多少、多久
- **根因**：为什么防线没拦住（对应第几层失守）
- **修复**：PR 链接
- **沉淀**：
  - [ ] 回归测试：<测试文件/脚本>
  - [ ] REVIEW.md 规则：<新增条目>
  - [ ] 防线改进：<改动点>
```

## 5. 与其他层的衔接

- 发布门禁（本层）复用第 4 层同一套测试，双保险：PR 进 main 一次、发版前一次；
- `/api/health` 的版本号来自 `server/package.json`，**发版前必须与 tag 同步更新**（打 tag 前先 bump 版本号提交）；
- 事故复盘产出直接喂给第 2 层（AI 审查章程 REVIEW.md），形成防线进化闭环。
